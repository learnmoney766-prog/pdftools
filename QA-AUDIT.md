PASS for PDF outputs means the generated bytes were saved as test artifacts, reopened with pdf-lib and independent PDF.js, and parsed with Poppler `pdfinfo`; content/page expectations were checked where applicable. The production watermark workflow additionally exercised the actual Blob-backed download link. The native browser save-to-disk event was not captured separately, so this audit validates the exact generated Blob bytes and download link rather than a filesystem readback from a browser download manager.

The supplied PDF reproduced the failure: its xref stream declared `/Size 17` while `/Index [0 18]` described entries through object 17, and Poppler emitted `Invalid 'size' inside xref table`. pdf-lib/PDF.js recovered by scanning objects, which masked the broken cross-reference. Watermarking in place retained the inconsistent object graph. Saving now copies the output pages into a fresh document context and writes a conventional xref table, repairing the malformed input structure before delivery.

## Problems discovered and fixes

- **Long watermark text was clipped.** Placement used unrotated text width, so rotated text could run beyond page edges. The watermark code now computes the rotated bounds, fits text per page, normalizes whitespace, and rejects text that cannot fit at a useful minimum size. Long diagonal labels rendered fully within mixed page sizes after the fix.
- **Unsupported watermark characters raised a low-level font exception.** The built-in Helvetica standard font uses a limited encoding. Unsupported characters now produce a useful validation error and no download; supported Western European text remains usable. This does not add full Unicode font embedding.
- **Malformed xref stream on the supplied watermarked PDF.** Independent Poppler inspection found an off-by-one `/Size` value. pdf-lib and PDF.js recovered the page by object scanning, but Poppler warned. The shared saver now rebuilds the document graph into a fresh PDF and serializes a conventional cross-reference table. The exact provided file was watermarked again; Poppler, pdf-lib, and PDF.js reopened the result, and the original content plus both watermark instances were visible.
- **Malformed input could be accepted by pdf-lib as a zero-page document.** The shared loader now rejects documents with no pages. Empty, corrupted, and renamed non-PDF fixtures were checked; errors are surfaced without output.
- **Page numbers could overflow tiny pages.** The placement now scales to page bounds and applies margins; a very small page was included in the regression cases.
- **Compression could derive bad viewport dimensions from a non-zero crop-box origin.** Width and height now come from the rotated viewport. Compression remains lossy rasterization and may increase file size; this audit did not freshly validate the post-change compression route in production.
- Shared PDF saving now checks the PDF signature/size, reopens the bytes with pdf-lib, and verifies page count before constructing an offered download. ZIP creation checks non-empty output, expected unique entries, sizes, MIME types, and image signatures before returning a Blob.

## Implementation inspected

- PDF editing, creation, serialization, and page operations use `pdf-lib` in `src/lib/pdf.ts`. PDF.js is dynamically imported in `src/lib/renderer.ts` for page rendering, text extraction, and previews. JSZip packages PDF-to-image outputs.
- Tool dispatch and controls are in `src/pages/ToolPage.tsx`; shared upload/output/status behavior is in `src/components/ToolParts.tsx`.
- PDF saves are validated before a Blob is offered. Output cards use Blob object URLs and revoke them when the output changes/unmounts. PDF.js render tasks are destroyed and canvas buffers cleared on completion/cleanup. Browser memory still bounds practical file sizes.
- Validation is based on file content/parser behavior, not extension alone. File sizes are capped; PDF processing limits are documented in the README.

## Tests performed

- `pnpm run typecheck` — passed.
- `pnpm run build` — passed; Vite production build and 20 direct route pages generated.
- `pnpm run qa:pdf-integrity` — passed, 43 assertions across 39 generated PDF files. The suite stores output artifacts under `work/pdf-integrity/`.
- `pnpm exec node work/qa-core.mjs` — passed for shared range/input/output helpers and ZIP checks.
- All 39 generated PDFs reopened with Poppler `pdfinfo`; PDF output was also reopened with pdf-lib and PDF.js. Selected rendered samples were inspected with Poppler rendering (watermark, page number, image-to-PDF).
- Production watermark browser run passed on the built app: output link was present for a long watermark; unsupported CJK/emoji text showed a friendly error and no success/download; a valid subsequent run succeeded. No console errors were observed.

## Blockers and limits

- The local browser security review timed out on the PDF-to-JPG file picker. The one permitted retry also timed out, and the browser tool explicitly disallowed another path around the review. Consequently PDF-to-JPG, PDF-to-PNG, and compression were not re-run end-to-end in the production browser after the latest changes. They are BLOCKED, not PASS.
- Browser click-to-disk download-manager readback was not captured. The exact Blob bytes were written and reopened by the integrity suite, and the production watermark download anchor was verified.
- Chrome/Edge/Firefox cross-browser and mobile interaction matrices were not performed. Reset-during-processing, navigation-away, repeated drag interactions, extreme-large PDFs, and rapid concurrent input changes were not exhaustively exercised. Shared guards and cleanup were inspected, but these are not claimed as tested.
- The original failing watermark source/output was not provided. Synthetic reproductions exposed clipping and unsupported Unicode handling but those cannot be asserted as the cause of the user's original unreadable file.
- Text extraction itself was tested; copy-to-clipboard behavior was not independently verified in this audit.
- Poppler emitted environment font warnings on some raster previews; structural parsing succeeded. It does not indicate corruption in those tested files.

## Recommendation

The tested PDF generation paths and production watermark flow show no remaining corruption in the exercised cases, and the production build succeeds. The toolkit is **not yet ready for an unconditional deployment sign-off**: PDF-to-JPG, PDF-to-PNG, and compression need a production browser rerun, and the reported original watermark failure should be tested against the actual source PDF/output if available. The ZIP validator and PDF byte validation are in place to prevent known-invalid outputs from being offered as success.
